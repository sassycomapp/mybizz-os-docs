# PDLF — The Project Development Lifecycle Framework
*What it is, where it came from, why it exists, and what it does for you*

---

## 1. Opening — The Heart of the System

Everything else in this system exists in service of one activity: building real, working Anvil.works applications, correctly, with a non-technical developer directing an AI agent that does the actual construction. Docs Manager keeps the map of that work honest against reality. mb-align-docs keeps the documents describing that work internally consistent with each other and with time. Both of those are real and necessary — but they are support structures. PDLF is the thing they're supporting. PDLF is where the actual building happens, and everything else in this document set exists, ultimately, to make PDLF's own output trustworthy.

That distinction matters, because it explains why PDLF looks the way it does — why it's stricter, more elaborate, and more deliberately engineered than almost anything else in this system. A stale README is an inconvenience. A silently wrong assumption baked into a live application, discovered only after it's shipped to a paying client, is a different order of problem entirely. PDLF exists because that second kind of failure is the one that actually costs something real, and because the person relying on the agent to get it right — you — cannot personally verify every line of what gets built. The agent is, in the truest sense, your consulting architect on every single project. PDLF is the discipline that keeps that architect honest, rigorous, and accountable, every single step of the way.

## 2. What PDLF Actually Is

PDLF — the Project Development Lifecycle Framework — is not a tool in the way a linter or a formatter is a tool. It is a **contiguous, stage-gated, memory-compounding workflow**: a single continuous chain that runs from the very first idea for a project all the way through to production deployment and beyond, in which every step's output becomes the next step's input, in which nothing can silently be skipped, and in which nothing that happened is ever forgotten between sessions.

It runs on OpenCode as its execution engine, and it coordinates four distinct capability layers, each doing a genuinely different job:

| Layer | What it is | What it contributes |
|---|---|---|
| **Workflow** | GStack skills | Structured planning reviews, design consultation, QA, code review, shipping |
| **Engineering discipline** | Matt Pocock skills | Domain modeling, ticket generation, architecture health, triage |
| **Ledger** | PostgreSQL (`pdlf` database) | The single, referentially-enforced source of truth for every step, gate, deviation, and thinking checkpoint |
| **Memory** | GBrain | A persistent knowledge base, queried before every step, synced after every task |

Underneath all four layers sits one governing relationship, stated as plainly as possible: **the developer is the decision-maker. The agent executes. The ledger records. GBrain remembers.** Every mechanism described in this document exists to keep that relationship intact — to make sure the agent never quietly becomes the decision-maker, that nothing the agent does goes unrecorded, and that nothing learned is ever lost.

## 2A. The Platform PDLF Builds For: Anvil.works

PDLF does not target generic software. It is built, specifically and exclusively, for Anvil.works, and understanding what Anvil actually is — and what makes it genuinely different from a conventional web stack — matters for understanding why several of PDLF's own design choices look the way they do.

Anvil is a full-stack web application framework in which the entire application — client-side browser code, the user interface itself, server-side logic, and the database — is written in nothing but Python. There is no separate JavaScript layer for the browser, no separate templating language for the interface, no separate query language for the data. A developer building on Anvil writes one language, once, for the whole application. The interface itself is typically built with a drag-and-drop visual designer in Anvil's own cloud editor, which also provides free, built-in application hosting with no separate deployment infrastructure to configure.

Two things about Anvil's engineering are worth knowing precisely, because they materially affect how PDLF operates. First, the runtime engine that actually serves an Anvil app is open source, released under the AGPL license, and can be run entirely outside Anvil's own hosted cloud editor — as a standalone app server on a developer's own infrastructure if that's ever wanted. This means an application built on Anvil is never permanently locked to Anvil's own hosting; the option to self-host the identical runtime exists from day one, and using the open-source runtime to host non-open-source applications is explicitly, deliberately permitted. Second, the standalone app server bundles its own PostgreSQL database and its own reverse proxy by default, meaning a locally-run Anvil app requires essentially no environment setup to get working — install, launch, done.

The practical benefits this brings to PDLF's actual development and hosting environment are substantial: one language across the entire stack means the domain modeling, ticketing, and code review disciplines PDLF applies at each step never have to reason about a client-server language boundary — a ticket for a UI change and a ticket for a server-side change are both, mechanically, Python work. Free, zero-configuration hosting removes an entire category of deployment complexity PDLF would otherwise have to manage. And the open-source, self-hostable runtime means the applications PDLF builds are never held hostage to a single vendor's infrastructure decisions.

There are real limitations too, worth stating plainly rather than glossing over. Anvil's visual, drag-and-drop interface designer is a proprietary tool with its own way of representing a UI — it does not export to, or import from, conventional external design tools. This has a direct, practical consequence covered fully in Section 2C below. And because the runtime's server component runs on the JVM, launching a local Anvil app server requires a working Java installation alongside Python — a second runtime dependency that a pure-Python framework wouldn't otherwise demand.

## 2B. Anvil Uplink — How PDLF Actually Tests Server Functions

A structural fact about Anvil worth understanding: an app's server-side code, by default, only runs inside Anvil's own hosted environment or the standalone app server — it isn't something arbitrary external Python code can simply call into or drive directly. The **Anvil Uplink** is the mechanism that closes this gap. It's a lightweight Python library that lets code running anywhere — a local script, a CI job, an agent's own test harness — connect to a live Anvil app and either call its server functions or expose new ones, over a real network connection to the actual running app.

There are two distinct Uplink privilege levels, and the distinction matters for how PDLF uses it. A **Server Uplink** connection behaves exactly like code running inside the app's own server module — full access to Data Tables, user management, and every `@anvil.server.callable` function, in both directions. A **Client Uplink** connection instead behaves like ordinary front-end form code — it can call already-exposed server functions, but cannot touch Data Tables directly or register new server functions of its own, the same restricted trust level browser-side code always has.

This is precisely the mechanism PDLF's own internal three-level feature testing depends on. Step 35's build loop tests every feature at three levels — pure logic, integration, and manual verification — and the integration level is where Uplink does its real work: rather than testing server-side logic in isolation with mocked inputs, PDLF's testing connects to the actual running app via the Uplink and calls its real server functions over a real connection, the same way the deployed application itself would be called. This is a meaningfully stronger test than pure unit testing alone — it exercises the genuine boundary between client and server exactly as production traffic would cross it, not an approximation of that boundary.

## 2C. Material 3 — PDLF's UI Standard, and Its One Real Caveat

Every application PDLF builds uses Anvil's Material 3 theme — Anvil's own implementation of Google's Material 3 design specification, distributed as an installable Anvil app dependency rather than a separate design toolkit. Building consistently on one theme, across every project PDLF touches, brings a specific and genuine benefit: a UI decision made once, correctly, in the design system carries forward automatically into every subsequent project, and a component built for one client application looks and behaves identically in the next, because both are drawing from the same underlying theme rather than being redesigned from scratch each time. This is a large part of why Magdoub's two-phase wireframe discipline (Section 3, and Steps 22/26 in the skill table) can move as fast as it does — the visual vocabulary it's iterating within is already fixed and shared, not reinvented per project.

The honest caveat, stated directly rather than left implicit: Anvil's own interface designer does not integrate with conventional external design tools — a Figma file cannot be imported into an Anvil app, and an Anvil form cannot be exported back out to Figma for a designer working outside the platform. Anyone used to a Figma-centered design workflow needs to recalibrate around Anvil's own visual builder instead. This is precisely why the Magdoub wireframe skill's role in PDLF matters as much as it does — it provides a structured, iterative design discipline that operates natively within the agent-driven workflow itself, rather than depending on an external design tool PDLF's actual platform can't talk to.

## 3. Origins — The Disciplines PDLF Was Built From

PDLF was not invented from nothing. It was assembled — deliberately, iteratively, and with real intellectual effort — out of several genuinely separate disciplines, each borrowed from a field that had already solved part of this problem well, then pulled apart, tested against real use, reworked where it didn't fit, and fused into a single coherent system. Understanding PDLF properly means understanding what each of these contributed, and why none of them alone would have been enough.

**From formal project-gating methodology: the stage-gate itself.** The idea that a project moves through distinct phases, and that a phase cannot begin until the previous one has been formally verified and signed off, is not a novel invention — it's a well-established discipline from structured project management, adapted here for a very different context: a single developer directing an AI agent, rather than a team moving a product through a corporate pipeline. What PDLF took from this discipline was the *hardness* of the gate — a gate is not a suggestion or a milestone marker, it is a genuine stop, and the pipeline structurally cannot proceed past it without explicit, recorded approval. What PDLF reworked was the scale: instead of gates spaced months apart across a large team, PDLF's seven gates are woven directly into a single continuous agent-driven build, at exactly the points where irreversible commitment starts to accumulate — the domain model, the concept, the wireframes, the architecture, the build itself, production, and release.

**From de Bono's thinking discipline: BFT.** This one deserves its own full treatment, and gets one in Section 5 below — but at the level of origin, what matters is this: PDLF needed a way to force genuine judgment at decision-heavy steps without either skipping thinking altogether or drowning every trivial step in the same heavyweight scrutiny. Edward de Bono's *Master Thinker's Handbook* supplied exactly that discipline, and it was adopted almost intact, then adapted specifically to fit the shape of a software build pipeline rather than a general thinking exercise.

**From database and transactional-systems engineering: referential integrity as memory.** Early versions of PDLF tried to track progress the way most ad hoc AI-assisted work still does — flat markdown files: a state snapshot, an audit log, and per-step completion reports. These three files could, and did, silently disagree with each other, because nothing enforced their agreement. What PDLF took from serious transactional systems engineering was the insight that *memory that can silently corrupt itself isn't real memory* — and the fix was to stop pretending markdown files could do a database's job. A relational ledger, with real foreign-key constraints, replaced all three flat files. Step 19 genuinely cannot be recorded as complete if Step 16 doesn't exist in the ledger — not because an agent remembered to check, but because the database itself refuses the insert.

**From software engineering minimalism: the skill-use principle.** A discipline familiar from decades of software engineering practice — often summarized as "do one thing well, and don't reach for a bigger tool than the job needs" — was adopted directly into PDLF as a governing rule: a specialized skill is invoked only when it does something better than the agent could do directly. This sounds obvious until you notice how rarely it's actually enforced in practice. PDLF enforces it by requiring the agent to read a skill's own definition before ever invoking it — never trust a name, never assume a skill does what it sounds like it does. This discipline has already caught real errors during PDLF's own construction: two entire steps were found to have no genuine downstream consumer and were removed outright, precisely because this principle was applied rigorously rather than taken on faith.

**From structured, multi-lens organizational review: GStack's contribution.** Real organizations don't approve a plan with a single reviewer — they run it past different lenses (leadership priorities, engineering feasibility, design coherence, developer experience) because each lens catches something the others miss. GStack brings exactly this discipline into PDLF, compressed into repeatable, invocable skills: a CEO-lens review, an engineering-lens review, a design-lens review, a developer-experience-lens review — each a genuinely different angle of scrutiny on the same plan, run in sequence, rather than one generic pass pretending to cover everything at once.

**From professional software engineering practice: Matt Pocock's contribution.** Domain modeling as a formal discipline — establishing a locked, shared vocabulary before any code gets written — and structured ticket decomposition, breaking a locked plan into concrete, tracer-bullet-sized units of work rather than one undifferentiated blob of "build the feature," are both established professional engineering practices. PDLF adopted them as named, invoked skills at exactly the points in the pipeline where their absence had previously caused real ambiguity.

**From UX and product design practice: Magdoub's contribution.** The two-phase wireframe discipline — black-and-white structural wireframes first, refined and polished wireframes only once the structure itself is approved — is a standard iterative design practice, borrowed directly from how real product design teams avoid wasting polish effort on a structure that hasn't been validated yet. PDLF gates on both phases separately for exactly this reason: approving structure and approving visual polish are genuinely different judgments, and collapsing them into one step would have let a bad structural decision hide behind good-looking visuals.

**From technical writing and instructional design: progressive disclosure.** Rather than one monolithic document trying to hold PDLF's entire procedure at once — which every earlier version of this system tried, and which became unreadable every single time — PDLF adopted progressive disclosure as an architectural principle: a lean control document holding only the step table and the control loop, with every genuinely detailed procedure living in its own file, loaded only at the step that actually needs it.

**And underneath every one of the disciplines above: deep, specific Anvil.works platform expertise — the one discipline PDLF cannot borrow from a generic engineering practice, because no generic practice knows how Anvil actually works.** PDLF does not build generic software. It builds Anvil applications, exclusively, and Anvil has its own deployment model, its own IDE-based publishing flow, its own sacred configuration file that must never be touched carelessly, its own environment mechanics that don't map cleanly onto how most other platforms work. This platform-specific layer comes from `anvil-agent-references` — a real, adopted skill library maintained by Anvil.works itself, generated directly from their own platform source rather than hand-written and left to drift, and structured as an installable set of individual skills covering exactly the areas PDLF's build steps touch most: server code, client forms, data models, and the rest of the platform's actual mechanics. This does not sit at the periphery of PDLF. It sits at PDLF's core, because every other discipline described above is, in the end, in service of building an Anvil application correctly. A stage-gate methodology, a thinking discipline, a relational ledger, structured reviews, domain modeling, iterative wireframing — none of it matters if the resulting build doesn't actually respect how Anvil itself works. This is the discipline that grounds all the others in the actual platform PDLF exists to build for, and it is one of five named components — alongside GStack, GBrain, Matt Pocock's skills, and Magdoub's wireframe skill — that make up PDLF's actual skill library, introduced properly in Section 7.

This is the honest shape of PDLF's origin: not one clever idea, but the deliberate synthesis of several genuinely proven disciplines, each contributing the part it does best, each reworked where a straight import didn't fit, assembled into something none of them could have been alone.

## 4. Why PDLF Exists — The Problem, Stated Plainly

Most AI-assisted development, left unstructured, fails in a specific and predictable way. The agent does work. The session ends. Context is lost. There is no continuity between planning and building — the agent that plans a feature on Monday has no reliable memory of that plan by Wednesday unless something external forces it to remember. There is no enforcement of discipline — nothing stops an agent from quietly skipping a step it finds inconvenient, deviating from an agreed plan without saying so, or doing manually, and worse, what a specialized skill exists to do properly. And there is no real traceability — when something goes wrong, there's often no way to reconstruct exactly what the agent actually did versus what it merely reported having done.

For a non-technical developer — someone who can read a plan and judge whether the resulting feature actually works, but who cannot personally verify every line of generated code — this isn't a minor inconvenience. It's the entire risk of the arrangement. You are trusting the agent's technical judgment because you have no realistic alternative. PDLF exists to make that trust *earned* rather than *assumed*, through six concrete mechanisms:

**Continuity.** The pipeline is a single, unbroken chain from idea to production. Every step feeds the next. The Postgres ledger survives any session boundary — closing your terminal, restarting your machine, coming back a week later, none of it matters. The ledger doesn't forget.

**Enforcement.** Each step is a hard gate at the phase level, and each step's own preconditions are checked before it runs at all. The agent genuinely cannot proceed to a step whose dependencies haven't completed — this is checked before the step even begins, against the explicit dependency table that governs the whole pipeline.

**Traceability.** Every step produces a Step Receipt generated directly from the ledger row that step just wrote. This is a deliberate design choice worth dwelling on: the receipt is not a summary the agent composes afterward, which could subtly diverge from what actually happened. The receipt *is* the ledger row, formatted for reading. There is no gap in which a narrative gloss could drift from the truth, because there is no separate narrative — only the record itself, made legible.

**Skill-use discipline.** A GStack or Matt Pocock skill is invoked only when it does something the agent genuinely couldn't do as well directly. This has already caught real errors during PDLF's own construction — skills that sounded right by name were found, on actually reading their source, to have no real consumer or no genuine advantage, and were removed rather than kept out of inertia.

**BFT — thinking discipline, not rubber-stamping.** Covered fully in the next section, but stated here as a design principle: the amount of deliberate thinking demanded at each step is proportional to how much judgment that step actually requires — heavy where real decisions are made, light where the decision was already locked earlier, none where the step is purely mechanical. No step gets a hollow, boilerplate gesture at thinking in place of real thinking.

**Compounding knowledge.** Every project's learnings, architecture decisions, and ideal-state definitions are stored in GBrain. The next project doesn't start from zero — it starts from everything every prior project already discovered.

The alternative to all of this — the thing that happens by default, without a framework like PDLF imposing structure — is not one dramatic failure. It's the same slow, silent erosion described elsewhere in this system's documentation: an agent proceeding confidently on an assumption nobody checked, a step quietly skipped under time pressure, a decision made and then genuinely forgotten by the next session, a plan that drifted from what actually got built with nobody able to say exactly when or why. PDLF's entire design is a rejection of that default.

## 5. BFT — BODY Frame Thinking, and Its Role in PDLF

**How it came to be.** BFT is drawn directly from Edward de Bono's *Master Thinker's Handbook*, and PDLF treats that book less as something to read cover-to-cover and more as a tool manual — a practical, applicable discipline rather than a philosophical text. De Bono's central premise, and the one PDLF inherits wholesale, is deceptively simple: good thinking is not intelligence. Good thinking is the deliberate, directed act of paying attention to the right things, in the right order, rather than trusting that intelligence alone will naturally arrive at a good answer. This premise mattered enormously to PDLF's design specifically because the alternative — trusting an intelligent agent to simply "think it through" at each step, with no structure — is exactly the rubber-stamping failure mode PDLF was built to eliminate.

**What it actually is.** BFT organizes attention around five body-part metaphors, each a genuinely different lens, plus a closing sixth check. BONES asks what the essential structural elements are — the handful of things that must exist for the situation to make sense at all, separated into the load-bearing major elements and the smaller elements that merely support them. MUSCLE asks what actually provides force and leverage — what is doing the real work of making this succeed, whether that's a constraint, an incentive, a resource, or plain momentum. NERVES asks how the parts communicate and coordinate — whether the task at hand calls for reaching a goal, exploring possibilities, breaking something apart analytically, or assembling execution, and whether the right network was actually used rather than an inappropriate one. FAT asks what is simply unnecessary — irrelevant detail, over-analysis that passed the point of usefulness, decorative complexity that feels intelligent without actually helping. SKIN asks how the result should be presented — is it genuinely understandable, is it easy to engage with, does its packaging and sequencing actually serve the person receiving it. And a final HEALTH check asks the plainest question of all: is this actually sound, does it actually work, and what happens if it's allowed to run forward in time.

**How it's applied inside PDLF.** BFT is not applied uniformly, and this is deliberate. Applying the full six-question discipline to every single step — including purely mechanical ones — would produce exactly the boilerplate, rubber-stamped answers the discipline exists to prevent; nobody generates genuine insight answering "what is the essential structure" of bumping a version number. So PDLF applies BFT at three distinct levels, matched to how much real judgment a step actually contains. Decision-heavy steps — architecture calls, scope decisions, design judgments, every gate — receive the Full treatment, all six questions, answered specifically to what just happened, never generically. Mostly mechanical steps that are simply executing an already-locked decision receive a Light pass — BONES and HEALTH only, enough to catch a real problem without manufacturing false depth. Purely mechanical, zero-judgment operations — a git pull, a file format conversion — receive no BFT at all, because there is no genuine judgment there to interrogate. And at every single gate, regardless of what level that step would normally receive, BFT reverts to Full without exception — because a gate is the one moment where a checkpoint is about to become permanent, and that moment always earns the complete discipline.

**Its contribution to discipline enforcement.** BFT's real contribution to PDLF isn't the six questions themselves — it's the enforcement mechanism sitting behind them: a required answer that's left blank, generic, or copy-pasted is treated as equivalent to no answer at all. A response has to be specific to the actual step that was just completed, or it doesn't count. This closes off the single most tempting failure mode in any AI-agent-driven pipeline — an agent that produces the *appearance* of careful thought (a filled-in checklist, a plausible-sounding justification) without the substance of it. BFT is PDLF's mechanism for making sure the thinking checkpoints scattered throughout the pipeline are actually thinking, not performance of thinking — and by scaling its intensity to where judgment genuinely lives, it manages to enforce that honesty without collapsing under its own weight at the steps that don't need it.

## 6. How PDLF Actually Works

### The step model, and who owns what

PDLF is a pipeline of canonical steps, numbered from 11 through 46 (with step 1 reserved for the orchestrator itself and steps 4 through 10 explicitly reserved for future use), grouped into five phases, plus a set of lettered sub-steps inserted specifically for testing and remediation within the build loop. A step number is a stable identity — it never changes what a step *is* — but it carries no information at all about *when* that step runs relative to any other step. That's a deliberate separation of concerns, split across two documents that each own exactly one side of it: one document is the sole authority on execution order, branching, and dependencies; a completely separate document is a pure lookup table answering "what is step N, and who handles it" — and it explicitly refuses to claim any sequencing authority of its own, even in its own internal formatting. Two documents each quietly claiming to govern sequence was found, during PDLF's own development, to be exactly the kind of duplicate-source-of-truth failure this whole system exists to prevent everywhere else — so it was corrected here too, structurally, not just by convention.

### Entry — new project or existing, handled the same way

Every step always runs, for every project, full stop — there is no shortcut sequence for an existing project and no separate audit branch deciding what to skip. This wasn't the original design; an earlier version of PDLF did try exactly that (an interactive audit assigning skip/re-run/run-as-new to each step), and it was deliberately retired once a simpler, more honest principle proved sufficient: submitting an existing project to PDLF means redeveloping it around its canonical concept, not auditing or patching what's already there. What differs between a brand-new project and an existing one is never *whether* a given step runs — only what material that step starts from. A new project's Step 11 fetches a fresh template and creates a full folder structure from scratch; an existing project's Step 11 instead verifies what's already there, creating only genuinely missing canonical folders and never overwriting real content. From Step 12 onward, both kinds of project run through literally the same sequence — if existing material already satisfies what a given step needs, that step simply completes quickly, not because anything decided to skip it, but because there was genuinely nothing left to change.

### The five phases

The pipeline moves through five phases, each with a clear entry condition (the prior phase's gate must have passed) and its own exit gate:

**Phase A — Discover & Define** runs initialization through domain modeling, ending at the `domain-locked` gate. This is where the project's foundational vocabulary and architectural decisions get pinned down — the domain glossary and the ADRs that will govern everything downstream.

**Phase B — Design & Plan** covers everything from creating the actual Anvil data tables through to wireframes and design review, with two exit gates: `concept-locked`, a full cross-document coherence audit that hard-freezes scope (no new feature can be added afterward without formally reopening the gate), and `wireframes-approved`, confirming both the structural and the polished wireframe passes are complete.

**Phase C — Scaffold & Assemble** covers building the actual UI forms and the physical scaffold in the Anvil IDE, ending at `architecture-verified` — the physical build confirmed to genuinely match the architecture that was locked earlier, before a single line of feature code is written.

**Phase D — Build & Verify** is where features actually get built, one at a time, in a loop described fully below, ending only once every feature individually reaches `build-verified`.

**Phase E — Ship & Monitor** covers shipping and production release, though it's worth being honest about this phase's current state: several of its steps were originally modeled on a generic staging/production environment split that turned out not to describe how this platform actually works at all (more on this below) — that portion of the phase is acknowledged as needing rework, without that fact changing anything about the rigor applied to the phases that come before it.

### The seven gates

A gate is not a milestone marker — it is a genuine, hard stop requiring explicit developer approval before the pipeline can proceed, and once passed, it cannot be silently unwound. Reopening a passed gate requires a formal, developer-authorized deviation, not a quiet backtrack. Every gate, without exception, follows the same ceremony: Full BFT regardless of what level the step would otherwise carry; full maintenance (both the code and documentation repositories committed and pushed, GBrain synced and embedded on both); a visually distinct gate summary presented to you; and your explicit yes-or-no approval before anything moves forward. The seven gates — `domain-locked`, `concept-locked`, `wireframes-approved`, `architecture-verified`, `build-verified` (evaluated once per feature, not once for the whole project), `production-released`, and `released` — mark every point in the entire pipeline where an irreversible commitment is about to be made.

### The thirteen-point execution sequence

Every single step in the pipeline, without exception, follows the same disciplined sequence. It queries GBrain for context relevant to that step's specific domain before doing anything else. It identifies what kind of step it is — a skill invocation, a manual action, an optional decision, or a gate — and routes accordingly. If the step is optional, it presents a recommendation with justification and waits for an explicit run-or-skip decision; it never decides this itself. If the step is manual, it presents instructions and waits for you to confirm the work is actually done, then verifies rather than trusting the confirmation blindly. If the step invokes a skill, it reads that skill's own definition first — never trusting a name alone — and invokes it properly. Once the step's work is done, it verifies the expected output genuinely exists; if it's missing, the step stops cold and raises a deviation request rather than quietly proceeding on an assumption. It runs the BFT checkpoint at whatever level that step is assigned. It writes the ledger row. It generates and saves the Step Receipt. It asks the two housekeeping questions — commit and push to GitHub, and sync and embed to GBrain — separately, every time, never combined into one question and never run automatically without being asked. And then it stops, reports to you, and waits for you to say "continue." No step, anywhere in this pipeline, from a purely mechanical git pull to the most consequential architecture gate, skips any part of this sequence without a formally recorded deviation.

### The deviation mechanism — never a silent skip

When a step genuinely cannot be completed as prescribed, the agent does not decide what to do about it. It stops and presents exactly three options: authorize a specific alternative action, decline and attempt to resolve the actual blocker instead, or explicitly skip the step and proceed, with the real impact of skipping stated plainly rather than glossed over. You decide. Every deviation, whichever option is chosen, is permanently recorded — the description of the problem, the exact options that were presented, and the decision made. This mechanism is also PDLF's answer to a subtler and arguably more dangerous situation: a genuine disagreement between what the agent observes in the actual files and what you, the developer, state to be true. That conflict is never silently accepted at face value and never merely logged for later — it's surfaced immediately and resolved on the spot as a formal deviation, precisely because letting evidence and stated belief quietly diverge, unaddressed, is exactly the kind of gap where real mistakes hide.

### The Postgres ledger — memory that cannot silently lie

The ledger is a dedicated PostgreSQL database holding seven tables, each tracking a genuinely distinct kind of fact: `projects` holds the registry of what projects exist, their mode, their filesystem paths, and their GBrain sources; `steps` holds the record of every step's status, type, and output artifact; `gates` records whether and when each gate was formally passed; `deviations` holds the full record of every blocker ever raised and how it was resolved; `bft_records` holds the actual answers given at every thinking checkpoint; `isc` holds the Ideal State Criteria that define what "done" concretely means for a project; and `triage_findings` holds every issue surfaced during testing and review, tracked through to its resolution.

Sequencing itself is worth being precise about, because it's a genuinely subtle point: the database's own foreign keys do not enforce step-to-step ordering directly — a live test confirmed that inserting a later step's row with no earlier step present would actually succeed at the schema level, because the dependency graph between steps varies too much per step to express as a fixed column constraint. The real enforcement happens one layer up: the orchestrator checks the explicit dependency table before it will write a step's row at all, and the only thing with legitimate access to write to this database in the first place is the orchestrator itself, operating through an actual PDLF step — a raw write bypassing that path is already a policy violation before it ever reaches the database. What the ledger's referential integrity *does* guarantee, absolutely, is that nothing recorded as complete can silently reference something that was never actually recorded — the two failure modes are different, and both are covered, just by different layers of the same system.

The Step Receipt — the thing you actually read after every step — is generated directly from whatever row was just written, not composed as a separate narrative. This is worth restating because it's the exact mechanism that makes the ledger trustworthy in practice: there is no gap in which an agent's summary of what happened could quietly diverge from what the database actually recorded, because the summary *is* the database record, formatted for a human to read.

### The feature build loop

Phase D's real substance is a loop, not a straight line: steps 35 through 39, including every lettered sub-step, repeat once for every individual feature drawn from the ticket list generated back in Step 19. A "feature," concretely, is an Anvil client-code package — authentication, a blog module, a CRM module, and so on — not an arbitrary unit of work; the loop's granularity is tied directly to how the application is actually structured in Anvil. The loop's own order is fixed and worth stating exactly as it runs: **35 → 35A → 40 → 40B → 36 → 37 → 38 → 38A → 39 → gate.** A feature is not considered complete until it has passed through that entire sequence and reached its own `build-verified` gate. Within one pass of the loop, a feature is built with three internal levels of testing — pure logic, integration, and manual verification — with a backup taken both before and after the integration level specifically. An optional, read-only architecture scan can run against that feature's code, and if it surfaces findings, you review and approve specifically which fixes get applied — the agent never applies architecture remediation unilaterally. Design review and code review both run *after* any remediation, not before, deliberately, so what actually gets tested is the feature as it will really ship, not an intermediate version that's about to change again. Code review and QA are both required to persist their findings to a named, checkable file path — including an explicit statement when the pass was clean — rather than the agent simply asserting a review happened. Triage then processes those findings, and the `build-verified` gate for that specific feature is evaluated as a pure query against the ledger: it passes only when every single triage finding for that feature is either marked as won't-fix or has a recorded resolution. No open findings, no exceptions. Only once every feature drawn from the original ticket list has individually reached this gate does the pipeline move on to shipping at all.

### The ISA — the thing that survives across projects

The Ideal State Artifact is the living, permanent definition of what "done" actually means for a given project — created early, updated at key points including the final LEARN step, and explicitly queried at the very start of the *next* project, so that what one project learned about defining done genuinely carries forward rather than starting over. Most of its sections are hand-authored — the problem statement, the vision, what's explicitly out of scope, the governing principles and constraints, and the single sentence that actually defines done for this specific initiative. But two of its sections are deliberately generated, not hand-edited at all — the criteria table and the verification table are both produced directly from the ledger's own criteria records, for exactly the same reason the Step Receipt is generated rather than composed: so the definition of "done" and the actual, checkable record of whether it was met can never quietly drift apart from each other.

### The learning loop — the LEARN junction, and what actually carries forward

Step 46 is named, deliberately, the LEARN junction rather than simply "the last step" — it's both a gate (`released`) and the point where a project's own accumulated experience gets formally closed out and handed forward, not just wrapped up. Three concrete things happen there, together: the ISA's Verification section is filled in against what actually shipped, its Changelog is updated with a final entry, and the project's own registry record is marked complete and inactive. None of this is narrative summary written after the fact — the ISA's own generated sections are pulled directly from the ledger's criteria records, the same anti-drift discipline used everywhere else in PDLF.

What actually compounds from one project to the next is the combination of two things working together, not one alone. The ISA is queried at the very start of the *next* initiative — so whatever that prior project learned about what "done" genuinely means for a class of work carries forward as a concrete artifact, not a memory someone has to reconstruct. And GBrain, synced throughout the project and again at this final gate, holds everything else — the ADRs, the domain decisions, the specific things that worked and didn't — queryable by any future project's very first step. Together, this is PDLF's actual learning loop: not a single mechanism at Step 46, but the LEARN junction closing out the record, the ISA carrying forward a concrete definition of done, and GBrain carrying forward everything else, indefinitely, project after project.

One honest note, rather than a confident answer: nothing in PDLF's own documentation, as it currently stands, names or defines a distinct "self-healing" mechanism — something that would autonomously detect and correct a problem without a developer decision in the loop. The closest adjacent things are the deviation mechanism (Section 6, above), which surfaces a blocker and requires an explicit developer choice rather than resolving anything on its own, and Step 45's canary monitoring at production, which observes for problems but doesn't itself remediate them. If a genuine self-healing capability is intended somewhere in PDLF's design, it isn't yet written down anywhere this document has access to — worth confirming directly rather than assuming it exists, or documenting it properly once it does.

### GBrain and the discipline of never trusting an indication

GBrain is queried automatically at the start of every single step — this is a read-only operation with no side effects, distinct from the deliberate, always-asked decision to sync and embed new content afterward. But there's a sharper discipline underneath this that's worth stating explicitly, because getting it wrong is genuinely dangerous: a GBrain query result is an *indication* of where relevant content lives, not the content itself. The required sequence, enforced deliberately rather than left to good intentions, is query, then indication, then actually fetching and reading the real file in full, and only then applying what it genuinely says. Treating a GBrain snippet as if it were the authoritative source — or worse, letting an agent quietly generate its own version of a standard it never actually read, while a GBrain query happened to run somewhere in the background — is precisely the failure mode this discipline exists to close off, because that failure looks exactly like compliance from the outside while producing content that never actually conformed to anything real.

### Housekeeping — asked, never assumed

At the end of every step, two questions are asked, always separately, never combined into one, and never run automatically: whether to commit and push this step's changes to GitHub, and whether to sync and embed this step's artifacts to GBrain. Both are real write operations with real consequences, and both remain entirely your decision, every single time, no matter how many times you've already said yes before.

## 7. The Skill Library — Five Components, and What Each One Actually Does For You

PDLF does not build its own review, testing, memory, or design tooling from scratch. It draws on a skill library of five named components, each adopted because it does something genuinely better than the agent could manage unaided, per the skill-use principle described earlier. Three of them — GStack, Matt Pocock's engineering skills, and Magdoub's wireframe skill — are invoked selectively, at specific named steps, and are covered in full in the step table below. The other two deserve their own proper treatment first, because their role in PDLF is different in kind, not just in degree, from an invoked-at-one-step skill.

**GBrain is not a skill invoked here and there — it is the memory the entire pipeline runs on, active at every single step.** Its two working mechanics are named, specific actions, not an abstraction: a query, run automatically and read-only at the start of every step to surface what's already known and relevant to that step's domain, and a sync — invoked deliberately, via `/sync-gbrain`, never automatically — that writes a step's new artifacts into that persistent memory once the developer explicitly approves it. This is what makes the "compounding knowledge" benefit described earlier a mechanical reality rather than a hopeful aspiration: every ADR, every domain glossary, every learning captured in one project genuinely becomes queryable context for every project that comes after it, because GBrain is the one component queried at every single step of every single project, without exception, forever. Nothing else in the skill library has that reach.

**`anvil-agent-references` is the platform-specific expertise layer PDLF's coding steps actually build against.** Where GStack and Matt Pocock contribute process discipline — how to review, how to model a domain, how to triage — `anvil-agent-references` contributes the raw, concrete knowledge of how Anvil.works itself actually works: server code conventions, client form behavior, data model mechanics, and the platform-specific detail that no generic software engineering skill could supply, because it's specific to one platform. It is expected to be deployed primarily in PDLF's coding steps — the scaffold-building and feature-build work of Phases C and D — where getting Anvil's own mechanics right is the difference between a feature that actually works on this platform and one that would work on a different platform but not this one.

## 7A. OpenCode — The Harness PDLF Actually Runs On

Every mechanism described in this document — the ledger writes, the skill invocations, the BFT checkpoints, the gate ceremonies — has to actually execute somewhere. That somewhere is OpenCode, an open-source AI coding agent harness, and PDLF's design leans on several of OpenCode's own capabilities specifically, not incidentally.

A harness, in the sense that matters here, is the layer that turns a language model into something that can actually read files, run commands, and carry out a multi-step task — as distinct from the model itself. OpenCode's harness provides the concrete mechanics PDLF's execution sequence depends on: real file edits, real shell execution, and a genuine agentic loop that analyzes a goal, chooses tools, acts, reads the result, and continues — not a single request-and-response exchange pretending to be a workflow.

Two things about OpenCode's own architecture map directly onto how PDLF is built. First, OpenCode already distinguishes between primary agents — the main assistant a developer interacts with directly, switchable between a full-access build mode and a read-only planning mode — and subagents, specialized assistants a primary agent can invoke for a narrow task, each configurable with its own restricted tool permissions. This is not a coincidence relative to how PDLF's own supporting skills (Docs Manager, mb-align-docs) are built: each of those skills' own subagents — a read-only detector, a text-only writer, a structural writer with elevated permissions — follows exactly the same primary-agent-plus-permission-scoped-subagent pattern OpenCode itself provides natively. Second, OpenCode's skill system is precisely the mechanism that makes PDLF's own skill library (Section 7 above) invocable at all — GStack, Matt Pocock's skills, Magdoub's wireframe skill, and `anvil-agent-references` are all installed and invoked as OpenCode skills, sharing one consistent installation and invocation model rather than each requiring its own separate integration.

**The WSL bridge** is a specific, practical consequence of this harness choice worth naming directly. PDLF's Postgres ledger runs on Windows, while OpenCode itself runs inside WSL (Windows Subsystem for Linux) — and WSL does not pass Linux environment variables through to a Windows executable directly. Rather than fighting that boundary, PDLF bridges it deliberately: OpenCode, from within WSL, shells out through PowerShell to reach the native Windows `psql` client and the Windows-hosted Postgres instance. This is a small, specific piece of plumbing, but it's a real example of a broader pattern in PDLF's design — where a genuine platform boundary exists, PDLF documents and bridges it explicitly, rather than working around it silently in a way that would eventually surface as a mysterious failure.

**The full loop, named plainly:** Anvil is the platform every application is actually built for and hosted on. GitHub is the versioned, permanent record of both the code repository and the documentation repository, committed and pushed at every gate and every housekeeping prompt. OpenCode is the harness that actually executes every step, invokes every skill, and writes every ledger row. And GBrain, covered fully next, is the memory layer queried and updated throughout. None of these four pieces substitutes for another — Anvil is the destination, GitHub is the permanent record, OpenCode is the executor, GBrain is the memory — and PDLF's own orchestration logic is the thing that keeps all four moving together in the right order.

## 7B. GBrain — Persistent Memory for Anvil Application Development, Specifically

Section 7 already introduced GBrain's role in PDLF at the conceptual level — a query at the start of every step, a deliberate sync afterward. It's worth being concrete about what that actually looks like in practice, because the mechanism is more capable than "search a knowledge base" suggests.

Once set up, GBrain gives an agent two genuinely different kinds of retrieval it wouldn't otherwise have. The first is semantic code search across a real, indexed codebase — not exact-string matching, but a ranked search by what code actually does, plus the ability to walk a call graph by symbol (find a function's definition, every place it's called from, everything it calls). The second, and the one that matters most for PDLF's own compounding-knowledge principle, is cross-session memory: plans, retrospectives, decisions, and learnings from every past session, genuinely searchable rather than something a developer has to manually recall and re-explain. A query like "what did we decide about the client instance architecture" returns the actual prior decision, not a request for the developer to re-describe context that already exists.

Keeping that memory current is a deliberate, separate action, not an automatic side effect — new content only enters GBrain through an explicit sync, run per-project, and PDLF's own housekeeping question at the end of every step ("sync and embed to GBrain?") is precisely that mechanism, asked every time, never silently skipped. This mirrors PDLF's broader "asked, never assumed" discipline from Section 6 exactly, applied to the memory layer specifically.

For Anvil application development in particular, this compounding memory has a genuine, compounding payoff across projects: an ADR written for one client application, a domain-modeling decision locked on a prior build, a pattern that worked well in one project's Anvil data table design — all of it becomes queryable context the next Anvil project can draw on automatically, at the very first step, rather than starting from a blank slate and re-deriving decisions PDLF has already made correctly once before.

## 8. The Rigor, Tied Together

It's worth stepping back and naming plainly what all of the mechanisms above actually add up to, because none of them individually is the point — the point is what they produce together. PDLF's own stated success criteria are worth stating in full, because they're a genuinely honest articulation of what this framework is actually trying to guarantee: **agent integrity** — the agent never simply acts and explains itself afterward; every decision has a traceable reason recorded at the moment it was made. **Build integrity** — what actually gets built matches what was actually agreed, with no silent scope drift. **Continuity** — a session can stop at literally any point and resume later with zero context lost. **Contiguity** — every step's output genuinely is the next step's input, with no gap where a decision can quietly fall through a crack. And **ease of use for a non-technical developer** — the entire system is built to work for someone relying on the agent's technical judgment precisely because they can't personally verify it line by line.

Every mechanism described in this document — the hard gates, the referentially-enforced ledger, the deviation-not-silent-skip discipline, BFT's proportional thinking checkpoints, the skill-use principle's insistence on reading before invoking, the requirement that GBrain results be fetched and read rather than merely indicated — exists in service of those five criteria, and nothing else. That's the actual shape of the rigor: not rigor for its own sake, but rigor specifically aimed at making it safe for someone who cannot check the agent's work directly to still trust the result.

## 9. The Benefits, Plainly Stated

What you actually get from working inside PDLF, rather than directing an agent through an unstructured build, is a project where nothing important was ever decided silently — every real judgment call is on record, with the reasoning attached, at the exact moment it was made. Where a lost session, a closed terminal, or a week's gap between sittings costs you nothing, because the ledger doesn't forget and doesn't need you to remember either. Where scope cannot quietly drift, because the gates that would need reopening to change it are hard, recorded, and require your explicit authorization. Where the thinking behind a decision-heavy step is genuinely present and specific, not a rubber-stamped gesture at having thought about it. And where every project you build makes the next one easier, because what was learned is captured permanently and queried automatically, not left to your own memory of a build that happened months ago.

## 10. Supporting Infrastructure — Docs Manager and mb-align-docs

PDLF does not operate in isolation, and it's worth being explicit about what supports it and how. As PDLF itself grows — and it already spans dozens of specifications, policies, ADRs, templates, and individual stepwise skill files, with more added as the remaining phases of the framework are built out — that body of documentation is exactly as vulnerable to drift and inconsistency as any other project's documentation would be. Docs Manager keeps PDLF's own navigational documents — its docmap, its step index, its README and AGENTS.md files — honest against what actually exists in `dev-makepdlf` and, once deployed, in `C:\pdlf\` itself. mb-align-docs keeps PDLF's own specifications, policies, and ADRs internally consistent with each other, their identities permanently tracked, their cross-references genuinely resolving to what's actually current. Neither skill has any special relationship with PDLF beyond this — they treat PDLF's documentation exactly as they'd treat any other project's — but that's precisely the point. PDLF enforces rigorous discipline on every application it builds; Docs Manager and mb-align-docs, in turn, enforce that same standard of honesty on PDLF's own documentation, so the framework holding everything else accountable is held to the identical standard itself.

## 11. Closing

**Simple. Secure. Robust. Fit for purpose.**

That's PDLF's own stated motto, and by the time you've seen the actual machinery — the gates that cannot be silently unwound, the ledger that cannot quietly disagree with itself, the thinking discipline that refuses boilerplate, the deviation mechanism that never lets a disagreement go unaddressed, the skills invoked only where they genuinely earn their place — it should read less like a slogan and more like an accurate description of what was actually built. PDLF is not simple in the sense of being basic; it's simple in the sense that every one of its many moving parts has one clear job, and none of them do anyone else's. It is secure in the sense that matters most for this specific situation: a non-technical developer, trusting an AI agent's judgment, protected by structural guarantees rather than good intentions. It is robust in the sense that a lost session, a disagreement, or a blocked step never produces silence or a guess — only a recorded, resolvable decision point. And it is fit for purpose in the most literal sense possible: built specifically, deliberately, and iteratively for exactly this task — turning an idea into a real, working Anvil application, with nothing important ever left to chance.
